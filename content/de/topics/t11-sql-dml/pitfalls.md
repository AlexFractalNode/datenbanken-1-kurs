# Typische Fehler: SQL-DML

1. **UPDATE oder DELETE ohne WHERE.** `UPDATE mitarbeiter SET gehalt = gehalt * 1.03;` soll nur eine Abteilung treffen. → Ohne WHERE ändert bzw. löscht das DBMS **jede** Zeile der Tabelle, ohne Rückfrage. → Richtig: Bedingung immer mitschreiben (`… WHERE abteilung_id = 3`) und vorher mit `SELECT … WHERE …` prüfen, welche Zeilen getroffen werden.
2. **Kindzeile vor der Elternzeile einfügen.** `INSERT INTO belegung …` für eine Person, die noch nicht in `schueler` steht. → Der Fremdschlüssel muss beim Einfügen auf eine vorhandene Zeile zeigen, sonst wird das INSERT abgewiesen. → Richtig: erst die Eltern (`person`, dann `schueler`), dann die Kinder (`belegung`). Bei gegenseitigen Verweisen eine Seite zunächst mit NULL einfügen und per `UPDATE` nachtragen.
3. **Identity-Werte selbst eintragen oder raten.** `INSERT INTO raum (raum_id, bezeichnung, …) VALUES (7, 'R203', …)` oder später `… VALUES (7, …)` in einer Kindtabelle, weil „die nächste Nummer ja 7 ist“. → Ein eigener Wert schiebt den Zähler nicht weiter, das nächste automatische INSERT kollidiert dann mit dem Primärschlüssel. Geratene Nummern stimmen nach Löschungen, Rollbacks oder parallelen Zugriffen nicht. → Richtig: Identity-Spalte weglassen und die neue ID mit `RETURNING` holen oder über einen eindeutigen fachlichen Wert nachschlagen (`INSERT … SELECT … WHERE email = …`).
4. **Mehrzeiliges VALUES in Firebird 3.** `INSERT INTO raum (bezeichnung, etage, plaetze) VALUES ('R203', 2, 4), ('Studio', 0, 8);` → Das ist PostgreSQL-Syntax, in Firebird 3 liefert `VALUES` genau eine Zeile. Ebenso gibt es dort kein `DEFAULT` als Wert in der Liste. → Richtig: je Zeile ein eigenes INSERT, Default-Spalten einfach weglassen. Kommen die Zeilen aus einer Abfrage, `INSERT … SELECT` verwenden.
5. **`VALUES` vor einem SELECT schreiben.** `INSERT INTO zahlung (…) VALUES (SELECT …)` für viele Zeilen. → `VALUES (…)` erwartet einzelne Werte. Eine Unterabfrage darin darf höchstens eine Zeile liefern, sonst gibt es einen Fehler. → Richtig: `INSERT INTO zahlung (…) SELECT … FROM … WHERE …` ohne `VALUES`.
6. **`= NULL` in der WHERE-Bedingung.** `UPDATE ausleihe SET rueckgabe = DATE '2025-01-31' WHERE rueckgabe = NULL;` → Ein Vergleich mit NULL ergibt UNKNOWN, die Anweisung trifft keine Zeile und meldet trotzdem keinen Fehler. → Richtig: `WHERE rueckgabe IS NULL`. Im SET ist `= NULL` dagegen korrekt, dort ist es eine Zuweisung (`SET provision = NULL`).
7. **Erwarten, dass eine Kaskade „so weit wie möglich“ löscht.** `DELETE FROM person WHERE person_id = 37` soll Person, Schülerzeile und Belegungen löschen, obwohl noch eine Ausleihe (`NO ACTION`) auf die Schülerin verweist. → Trifft die Kaskade auf eine Sperre, wird die **ganze** Anweisung zurückgenommen. Es bleibt nichts halb gelöscht. → Richtig: alle Ebenen der Kette prüfen. Erst die blockierenden Kindzeilen bearbeiten (Ausleihe abschließen und löschen oder umhängen), dann löschen.
8. **Skalare Unterabfrage im SET, die mehrere oder keine Zeilen liefert.** `UPDATE kurs SET raum_id = (SELECT raum_id FROM raum WHERE hat_klavier = TRUE) WHERE …` → Liefert die Unterabfrage mehrere Zeilen, bricht das UPDATE ab. Liefert sie keine, ist ihr Wert NULL. Bei einer NULL-fähigen Spalte wird der alte Wert dann still überschrieben, bei einer NOT-NULL-Spalte scheitert das ganze UPDATE. Dasselbe gilt für `SUM` über keine Zeilen (`COUNT` liefert dagegen 0). → Richtig: die Unterabfrage über einen eindeutigen Wert eingrenzen (`WHERE bezeichnung = 'Saal'`), die WHERE-Bedingung auf Zeilen beschränken, für die es einen Wert gibt, oder aggregieren und mit `COALESCE` einen Ersatzwert vorsehen.
9. **Erwarten, dass SET NULL die Kette fortsetzt oder immer gelingt.** `projekt.leiter_id` hat `ON DELETE SET NULL`, und man rechnet damit, dass beim Löschen der Person auch die Meilensteine des Projekts verschwinden. → SET NULL ändert nur die FK-Spalte, die Kindzeile bleibt, und für deren Kinder passiert nichts. Ist die FK-Spalte NOT NULL, scheitert SET NULL sogar, und die ganze Anweisung wird abgewiesen. → Richtig: Bei SET NULL und SET DEFAULT endet die Kette. Vorher prüfen, ob die FK-Spalte NULL zulässt.
10. **SET DEFAULT ohne passende Elternzeile.** `teilnahme.gruppe_id DEFAULT 0 … ON DELETE SET DEFAULT`, aber in `gruppe` gibt es keine Zeile 0. → Der Default wird zum Fremdschlüsselwert und muss deshalb selbst in der Elterntabelle vorkommen. Fehlt er, wird jedes DELETE einer verwendeten Gruppe abgewiesen. → Richtig: eine Platzhalterzeile (`gruppe_id = 0`, „ohne Gruppe“) anlegen und nicht löschen.
11. **TRUNCATE wie ein schnelles DELETE behandeln.** `TRUNCATE TABLE kunde` in PostgreSQL, weil die Tabelle „sowieso geleert werden soll“, oder in Firebird 3. → Firebird 3 kennt TRUNCATE nicht. In PostgreSQL laufen keine ON-DELETE-Trigger, Fremdschlüssel anderer Tabellen auf `kunde` lassen es scheitern, und `TRUNCATE … CASCADE` leert die verweisenden Tabellen vollständig mit. → Richtig: `DELETE FROM kunde` verwenden, wenn Trigger und referenzielle Aktionen wirken sollen oder Firebird im Spiel ist.
12. **Ganzzahldivision beim Rechnen im SET.** `SET betrag = gebuehr * (1 - rabatt / 100)` mit `rabatt` als INTEGER. → `rabatt / 100` teilt zwei ganze Zahlen und ergibt 0 (bei Rabatten unter 100), der Rabatt verschwindet ohne Fehlermeldung. → Richtig: erst multiplizieren, dann teilen (`gebuehr * (100 - rabatt) / 100`) oder durch `100.0` teilen.
13. **Zahlen und Daten als beliebige Zeichenketten einfügen.** `VALUES ('Quark', 'zwei Euro')` in eine NUMERIC-Spalte oder `'2025-13-01'` in eine DATE-Spalte. → Das DBMS wandelt Literale nur um, wenn sie einen gültigen Wert des Spaltentyps darstellen. Sonst wird die Anweisung abgewiesen. → Richtig: Zahlen ohne Anführungszeichen schreiben (`2.20`), Datumswerte als `DATE '2025-03-01'`.
