# Typische Fehler: Views, Trigger, Stored Procedures, Index

1. **Glauben, eine Sicht speichere eine Kopie der Daten.** „Die Sicht `v_kursplan` ist von gestern, ich muss sie neu anlegen.“ → Eine normale Sicht speichert nur ihre Abfrage. Bei jedem Zugriff wertet das DBMS sie auf den aktuellen Tabellen aus, sie ist also nie veraltet. Nur eine materialisierte Sicht hält ein gespeichertes Ergebnis (in PostgreSQL, nicht in Firebird 3). → Richtig: Sicht anlegen und einfach abfragen. Neu anlegen muss man sie nur, wenn sich die Definition ändern soll (`CREATE OR ALTER VIEW` in Firebird, `CREATE OR REPLACE VIEW` in PostgreSQL).
2. **Über jede Sicht ändern wollen.** `UPDATE v_abteilungsstatistik SET gehaltssumme = 20000 WHERE …` → Bei Join, GROUP BY, Aggregaten, DISTINCT oder berechneten Spalten kann das DBMS eine Änderung nicht eindeutig einer Basiszeile zuordnen. Die Sicht ist nur lesbar. → Richtig: direkt in der Basistabelle ändern oder, wenn es über die Sicht gehen muss, Trigger auf der Sicht schreiben, die die Änderung selbst umsetzen. Vorsicht in Firebird: Laut Referenz gibt Firebird Änderungen über eine Sicht mit eigenen Triggern **nicht mehr automatisch** an die Basistabelle weiter, auch wenn sie vorher änderbar war. Ein bloßer Protokolltrigger an einer änderbaren Sicht kann die Änderungen also stilllegen. Wer Trigger an eine Sicht hängt, behandelt deshalb am besten alle Ereignisse (INSERT, UPDATE, DELETE) selbst.
3. **`WITH CHECK OPTION` vergessen und sich über „verschwundene“ Zeilen wundern.** Über `v_klavierraum` (nur Räume mit Klavier) wird `SET hat_klavier = FALSE` ausgeführt. → Ohne Check Option ist die Änderung erlaubt, die Zeile fällt danach aus der Sicht heraus, und wer nur die Sicht sieht, kann sie nicht mehr zurückholen. → Richtig: Soll eine Sicht nur Zeilen erzeugen, die sie selbst zeigt, `WITH CHECK OPTION` anhängen (das setzt eine WHERE-Bedingung voraus). In Firebird zusätzlich beachten: Die Prüfung läuft, bevor etwas an die Basistabelle geht, deren Defaults und Trigger können eine verletzende Eingabe also nicht mehr korrigieren. Im INSERT fehlende Sichtspalten werden bei Check Option als NULL weitergereicht, Defaults greifen dann nicht; ohne Check Option greifen sie.
4. **In einem AFTER-Trigger `NEW` ändern wollen.** `ACTIVE AFTER INSERT … NEW.inventar_nr = UPPER(NEW.inventar_nr);` → Nach dem Schreiben ist `NEW` nur lesbar, Firebird lehnt die Zuweisung ab. `OLD` ist ohnehin nie änderbar. → Richtig: Werte, die mit der Zeile gespeichert werden sollen, in einem **BEFORE**-Trigger setzen. AFTER-Trigger für Protokolle und Folgeänderungen in anderen Tabellen verwenden.
5. **Trigger ohne `SET TERM` in isql eingeben.** Das Skript bricht schon nach `NEW.rabatt_prozent = 25;` mit einem Syntaxfehler ab. → isql beendet die Anweisung beim ersten Semikolon, also mitten im Rumpf. → Richtig: vorher `SET TERM ^ ;`, den Trigger mit `END^` abschließen, danach `SET TERM ; ^`. In grafischen Werkzeugen oder Programmen, die eine Anweisung am Stück senden, ist das nicht nötig.
6. **Vergleich mit `<>` bei NULL-fähigen Spalten im Protokolltrigger.** `IF (NEW.provision <> OLD.provision) THEN INSERT INTO …` → Wechselt der Wert von NULL auf 300 oder umgekehrt, ergibt `<>` UNKNOWN, und der Trigger protokolliert nichts. Außerdem läuft der Trigger je geänderter Zeile, nicht einmal je Anweisung. → Richtig: `IF (NEW.provision IS DISTINCT FROM OLD.provision) THEN …`. Das behandelt NULL wie einen gewöhnlichen Wert.
7. **Eine selektierbare Prozedur mit `EXECUTE PROCEDURE` aufrufen.** `EXECUTE PROCEDURE kurs_auslastung(1);` liefert nur eine Zeile, obwohl die Lehrkraft drei Kurse hat. → Eine Prozedur mit `SUSPEND` ist für `SELECT` gedacht. `EXECUTE PROCEDURE` holt nur den ersten Satz Ausgabewerte. → Richtig: `SELECT * FROM kurs_auslastung(1);` für selektierbare, `EXECUTE PROCEDURE …` für ausführbare Prozeduren.
8. **„Viel hilft viel“ bei Indexen, Reihenfolge egal.** Auf jede Spalte von `messwert` kommt ein eigener Index, auch auf `geprueft` (ja/nein); ein Index auf `(nachname, vorname)` soll auch `WHERE vorname = 'Ida'` beschleunigen. → Ein Index ist gespeicherte Redundanz: Jede Schreibänderung, die seine Spalten berührt, muss auch im Baum nachgetragen werden, und `messwert` bekommt alle zehn Minuten 200 neue Zeilen. Trifft eine Bedingung wie `geprueft = FALSE` ohnehin jede zweite Zeile, ist Durchlesen billiger als Anspringen, der Index bleibt ungenutzt. Ein zusammengesetzter Index ordnet zuerst nach der ersten Spalte; ohne Bedingung auf sie (oder bei `LIKE '%…'`) fehlt der Einstiegspunkt. → Richtig: Indexe gezielt für häufige, selektive Bedingungen anlegen, bei mehreren Bedingungen die Gleichheitsspalte nach vorn. Für Primärschlüssel und UNIQUE (in Firebird auch Fremdschlüssel) existiert schon einer.
