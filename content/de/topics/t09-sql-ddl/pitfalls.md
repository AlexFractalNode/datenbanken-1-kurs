# Typische Fehler: SQL-Grundlagen & DDL

1. **`NOT NULL` vor `DEFAULT` schreiben.** `zustand VARCHAR(10) NOT NULL DEFAULT 'neu'` → In Firebird ein Syntaxfehler, weil dort der Default vor den Constraints stehen muss. PostgreSQL nimmt beide Reihenfolgen an, deshalb fällt der Fehler oft erst in der Klausur auf. → Richtig: `zustand VARCHAR(10) DEFAULT 'neu' NOT NULL`.
2. **`ALTER TABLE … ADD` wie in anderen Dialekten schreiben: mit `COLUMN` oder mit Klammern.** `ALTER TABLE kunde ADD COLUMN geburtstag DATE` oder `ALTER TABLE kunde ADD (geburtstag DATE, newsletter BOOLEAN)` → Firebird 3 erwartet nach `ADD` direkt die Spaltendefinition, ohne `COLUMN` und ohne Klammern. Die Klammerform stammt aus anderen Dialekten bzw. aus `CREATE TABLE`. → Richtig: `ALTER TABLE kunde ADD geburtstag DATE, ADD newsletter BOOLEAN`. Jeder Teilbefehl bekommt sein eigenes `ADD` und wird mit Komma angehängt. Das läuft auch in PostgreSQL. Ebenso `ALTER TABLE kunde DROP geburtstag`.
3. **`ON DELETE RESTRICT` in Firebird 3.** → Firebird 3 kennt nur `NO ACTION`, `CASCADE`, `SET NULL` und `SET DEFAULT`. → Richtig: `ON DELETE NO ACTION` schreiben oder die Klausel weglassen. Ohne Angabe gilt `NO ACTION`, und Löschen mit vorhandenen Kindzeilen wird abgewiesen.
4. **`ON DELETE SET NULL` auf einer `NOT NULL`-Spalte oder `SET DEFAULT` ohne Platzhalter-Zeile.** Die Tabelle lässt sich anlegen, aber jedes `DELETE` einer referenzierten Zeile scheitert. → Falsch, weil SET NULL den NOT-NULL-Constraint nicht außer Kraft setzt und SET DEFAULT nur funktioniert, wenn der Default-Schlüssel in der Elterntabelle existiert. → Richtig: Für SET NULL die FK-Spalte NULL-fähig machen. Für SET DEFAULT eine Platzhalter-Elternzeile anlegen (z. B. Schlüssel 0, „nicht zugeordnet“) und diesen Wert als Default setzen. Oder eine andere Aktion wählen.
5. **Zusammengesetzten Primärschlüssel als zwei Spalten-PKs schreiben.** `helfer_id INTEGER PRIMARY KEY, schicht_id INTEGER PRIMARY KEY` → Falsch, weil das zwei Primärschlüssel wären und das DBMS die Tabelle ablehnt. Gemeint ist die Eindeutigkeit der Kombination. → Richtig: `CONSTRAINT pk_einsatz PRIMARY KEY (helfer_id, schicht_id)` als Tabellen-Constraint.
6. **Tabellen in der falschen Reihenfolge anlegen oder löschen.** `CREATE TABLE sitzplatz (… REFERENCES saal …)` vor `CREATE TABLE saal`, bzw. `DROP TABLE theater`, solange `saal` darauf verweist. → Ein FK braucht eine bereits existierende Zieltabelle (Ausnahme: Selbstbezug), und `DROP TABLE` scheitert, solange ein FK auf die Tabelle zeigt. → Richtig: anlegen von den Eltern zu den Kindern, löschen umgekehrt. Bei Zyklen einen FK erst nachträglich per `ALTER TABLE … ADD CONSTRAINT` anlegen und vor dem Löschen per `DROP CONSTRAINT` entfernen.
7. **Geldbeträge als Gleitkommazahl oder die Obergrenze nur über die Präzision.** `betrag DOUBLE PRECISION` bzw. `betrag NUMERIC(6,2)` in der Annahme, mehr als 9999,99 sei damit ausgeschlossen. → Binäre Gleitkommazahlen speichern viele Dezimalbrüche nur näherungsweise, Summen weichen dann um Rundungsreste ab. Und Firebird 3 erzwingt die Präzision von `NUMERIC` nicht: Intern steht eine ganze Zahl, und auch 99 999,99 wird angenommen (PostgreSQL lehnt es ab). → Richtig: `NUMERIC(p,s)` für Geld und eine fachliche Obergrenze per CHECK, am besten in einer Domäne: `CREATE DOMAIN d_euro AS NUMERIC(6,2) CHECK (VALUE BETWEEN 0 AND 9999.99)`.
8. **Postleitzahl oder Telefonnummer als `INTEGER`.** → Falsch, weil die führende Null verloren geht (01067 → 1067) und Zeichen wie `+` oder Leerzeichen nicht passen. Mit diesen Werten rechnet niemand. → Richtig: `CHAR(5)` für deutsche PLZ, `VARCHAR(20)` für Telefonnummern.
9. **Annehmen, ein CHECK verbiete NULL.** `CHECK (rabatt BETWEEN 0 AND 50)` soll fehlende Rabatte verhindern. → Falsch, weil die Bedingung mit NULL UNKNOWN ergibt, und ein CHECK lehnt nur FALSE ab. → Richtig: zusätzlich `NOT NULL` angeben, wenn der Wert Pflicht ist.
10. **Das NULL-Verhalten von UNIQUE auf alle Fälle übertragen.** Typische Annahmen: „UNIQUE erlaubt nur eine NULL“ oder umgekehrt „NULL stört bei UNIQUE nie“. → Bei **einspaltigem** UNIQUE sind in Firebird 3 und PostgreSQL beliebig viele NULL erlaubt. Bei **mehrspaltigem** UNIQUE mit teilweise NULL weicht Firebird 3 ab: Zwei Zeilen `(5, NULL)` gelten dort als Duplikat, nur `(NULL, NULL)` ist mehrfach erlaubt. PostgreSQL nimmt `(5, NULL)` beliebig oft an. → Richtig: Ist ein Wert Pflicht, `NOT NULL UNIQUE` schreiben. Ein mehrspaltiges UNIQUE möglichst nur über NOT-NULL-Spalten legen oder den Dialektunterschied ausdrücklich einplanen. PostgreSQL bietet für „höchstens eine NULL“ `UNIQUE NULLS NOT DISTINCT`.
11. **NOT-NULL-Spalte ohne Default zu einer gefüllten Tabelle hinzufügen.** `ALTER TABLE artikel ADD gewicht_g INTEGER NOT NULL` → Scheitert in Firebird 3, sobald die Tabelle Zeilen enthält, denn die alten Zeilen hätten keinen Wert. → Richtig: mit Default in einem Schritt (`ADD gewicht_g INTEGER DEFAULT 0 NOT NULL`, alte Zeilen bekommen 0) oder NULL-fähig anlegen, per `UPDATE` füllen und dann `ALTER TABLE artikel ALTER COLUMN gewicht_g SET NOT NULL`.
12. **Sich darauf verlassen, dass ein neuer CHECK die Altdaten prüft.** `ALTER TABLE gericht ADD CONSTRAINT ck_gericht_preis CHECK (preis > 0)` → Firebird testet die vorhandenen Zeilen dabei nicht, alte Verstöße bleiben unbemerkt in der Tabelle. PostgreSQL prüft sie dagegen und bricht ab. → Richtig: vorher `SELECT … WHERE NOT (preis > 0)` ausführen und Verstöße bereinigen.
13. **Identity-Zähler wie in PostgreSQL lesen oder von Hand füttern.** `GENERATED BY DEFAULT AS IDENTITY (START WITH 1000)` soll als erste Nummer 1000 liefern, `ALTER COLUMN id RESTART WITH 1000` ebenso. Oder es werden eigene IDs eingefügt (`INSERT INTO kunde (kunde_id, name) VALUES (5, 'Kaya')`). → In Firebird 3 ist der Startwert der Stand **vor** der ersten Nummer, nach `START WITH 1000` und nach `RESTART WITH 1000` kommt also 1001. Eigene IDs schieben den Zähler nicht weiter. Erreicht er später die 5, scheitert ein INSERT ohne ID am Primärschlüssel. → Richtig: für erste Nummer 1000 in Firebird 3 `START WITH 999` bzw. `RESTART WITH 999` schreiben, in PostgreSQL 1000. Die ID-Spalte im INSERT weglassen.
14. **Eine Sequenz als `DEFAULT` in Firebird verwenden.** `beleg_nr INTEGER DEFAULT NEXT VALUE FOR seq_beleg` → Firebird erlaubt als Default nur ein Literal, `NULL` oder eine Kontextvariable wie `CURRENT_DATE`. → Richtig: Identity-Spalte verwenden, den Wert im INSERT holen (`VALUES (NEXT VALUE FOR seq_beleg, …)`) oder einen Trigger schreiben. In PostgreSQL ginge `DEFAULT nextval('seq_beleg')`.
15. **Spalten und Constraints „umschreiben“, als wären sie unabhängig.** `ALTER TABLE zimmer ALTER COLUMN betten TO bettenzahl`, obwohl `ck_zimmer_betten` die Spalte nutzt, oder `ALTER CONSTRAINT ck_zimmer_betten CHECK (…)`. → Firebird 3 benennt keine Spalte um, die in einem Constraint (PK, UNIQUE, FK, CHECK), Trigger, einer Prozedur oder Sicht vorkommt. Eine `ALTER CONSTRAINT`-Form für Bedingungen gibt es nicht. PostgreSQL ändert damit nur Eigenschaften von Fremdschlüsseln. → Richtig: Constraint löschen, Spalte umbenennen bzw. Bedingung neu formulieren, Constraint neu anlegen: `DROP CONSTRAINT ck_zimmer_betten`, `ALTER COLUMN betten TO bettenzahl`, `ADD CONSTRAINT ck_zimmer_betten CHECK (bettenzahl BETWEEN 1 AND 6)`.
