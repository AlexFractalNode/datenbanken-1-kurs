# Typische Fehler: Datenbankmodelle & Architektur

1. **Datenbankmodell und Schema gleichgesetzt.** „Das Datenbankmodell der Kletterhalle besteht aus den Tabellen Mitglied, Besuch und Route.“ → Falsch, weil das die konkrete Struktur einer Anwendung ist, also ihr Schema. Das Datenbankmodell bzw. Datenmodell im allgemeinen Sinn (z. B. relational) legt nur fest, *mit welchen Mitteln* man Schemata beschreibt: Strukturen, Operatoren, Integritätsbedingungen. → Richtig: „Das Schema der Kletterhalle ist nach dem relationalen Datenbankmodell aufgebaut.“
2. **Verkürzung als Fehler des Modells gedeutet.** „Das Modell ist unvollständig, weil die Augenfarbe der Mitglieder fehlt.“ → Falsch, weil das Weglassen unwichtiger Eigenschaften gerade ein Merkmal jedes Modells ist (Verkürzungsmerkmal). Ob etwas fehlt, entscheidet allein der Zweck (pragmatisches Merkmal). → Richtig: Ein Modell nur danach beurteilen, ob es für den vorgesehenen Zweck alle nötigen Eigenschaften enthält.
3. **Netzwerkmodell als „relational mit Zeigern“ beschrieben.** In der Antwort heißt es, Netzwerkdatenbanken hätten Tabellen und SQL, nur zusätzlich Verweise. → Falsch, weil Netzwerkdatenbanken Datensätze über gespeicherte Verweise verbinden, an denen das Programm entlangnavigiert; deklarative Anfragen wie in SQL gibt es dort nicht. → Richtig: hierarchisch = Baum, genau ein Elternsatz; Netzwerk = Graph, mehrere übergeordnete Sätze möglich; beide navigierend. Relational = Beziehungen über gleiche Werte, deklarative Anfragen.
4. **Objektrelational und objektorientiert verwechselt.** „PostgreSQL ist eine objektorientierte Datenbank, weil es Tabellenvererbung kennt.“ → Falsch, weil PostgreSQL ein relationales System mit objektorientierten Erweiterungen ist, also objektrelational. Eine Objektdatenbank speichert Objekte direkt mit OID und Kapselung, ohne Tabellen als Grundlage. → Richtig: Grundlage Tabellen + SQL, ergänzt um Typen, Methoden, Vererbung → objektrelational. Grundlage Objekte und Klassen → objektorientiert.
5. **Externe Ebene nur als „die Benutzeroberfläche“ beschrieben.** „Die externe Ebene ist das Programm, das der Benutzer sieht.“ → Ungenau, weil die externe Ebene ein *Schema* ist: die Beschreibung, welchen Ausschnitt der Daten eine Benutzergruppe in welcher Form sieht (z. B. eine Sicht, siehe t12). Formulare und Listen sind nur Beispiele dafür. → Richtig: „Die externe Ebene enthält viele externe Schemata, je eines pro Benutzergruppe oder Anwendung, jeweils als Ausschnitt des konzeptionellen Schemas.“
6. **Index als logische Änderung eingeordnet.** „Ein neuer Index ändert die Datenbankstruktur, das ist logische Datenunabhängigkeit.“ → Falsch, weil ein Index eine Zugriffsstruktur der internen Ebene ist; Tabellen, Spalten und Beziehungen bleiben gleich. → Richtig: Index, Speicherort, Dateiorganisation → intern → physische Datenunabhängigkeit. Neue Spalte, Zerlegung einer Tabelle, Umbenennung → konzeptionell → logische Datenunabhängigkeit. Probe über die typische Anweisung: `CREATE INDEX` oder eine geänderte Dateiorganisation (Heap, B-Baum, Hash) → intern; Änderung an `CREATE TABLE`/`ALTER TABLE` → konzeptionell; nur `CREATE VIEW` → extern.
7. **Logische Datenunabhängigkeit als grenzenlos dargestellt.** „Dank Sichten bleibt jede Anwendung bei jeder Schemaänderung unverändert.“ → Falsch, weil eine Sicht nur Daten zeigen kann, die noch vorhanden sind. Löscht man eine benötigte Spalte, ist die Information weg. Außerdem greift die Unabhängigkeit nur, wenn Anwendungen über Sichten oder feste Spaltenlisten zugreifen, nicht mit `SELECT *` direkt auf Basistabellen. → Richtig: Logische Datenunabhängigkeit gilt nur für informationserhaltende Änderungen und setzt eine stabile Schnittstelle voraus. Sie ist schwerer erreichbar als die physische.
8. **Verwechslungsgefahr: ANSI-SPARC-Ebenen und Entwurfsphasen.** „Konzeptionelle Ebene = ER-Diagramm, interne Ebene = Tabellen.“ → Die erste Hälfte ist je nach Lesart vertretbar, die zweite ist falsch. In der **engen Lesart** (Architektur der laufenden Datenbank) steht auf der konzeptionellen Ebene das logische Gesamtschema, bei relationalen Systemen also die Tabellen. In der **weiten Lesart** (Ebenen mit dem Entwurf verbunden) stehen dort das ER- bzw. semantische Schema *und* das daraus abgeleitete Tabellenschema. Im Drei-Ebenen-Modell gehören die Tabellen in keiner Lesart auf die interne Ebene; dort liegen Dateien, Seiten, Dateiorganisation und Indexe. Nur eine vierstufige Lehrbuchvariante (extern, konzeptionell, intern, physisch) nennt das DBMS-spezifische Tabellenschema „intern“ – wer sie verwendet, muss das dazusagen. Zusätzlich verwirrt das Phasenmodell des Entwurfs (t03), das ER-Modell *konzeptuell* und Tabellen *logisch* nennt. → Richtig (Drei-Ebenen-Modell): Tabellen auf die konzeptionelle Ebene, Speicherstrukturen auf die interne; sagen, welche Lesart bzw. welches Begriffssystem du verwendest, und die Lesart deiner Lehrveranstaltung nutzen.
